📦 DTO — Data Transfer Object

💡 Principe fondamental
Chaque couche ne connaît que la couche juste en dessous. Le Controller ne parle jamais au Repository. Le Repository ne contient aucune logique. Tout le raisonnement "si/alors" vit dans le Service — exactement comme un cuisinier qui ne va jamais lui-même au frigo.
🔄

Flux complet — Côté restaurant

Ce qui se passe dans chaque rôle, de la commande à la livraison

1
🧑 Client regarde la Carte (API)

"Je vais commander une pizza Margherita" — il choisit dans la liste de ce qui est disponible, puis passe sa commande : POST /commandes {"nom":"Margherita"}

↓
2
📞 Standardiste (Controller) reçoit la commande

Vérifie que la commande est correcte : "Le nom est-il rempli ? La table existe-t-elle ?" Si c'est invalide → répond immédiatement 400 Bad Request. Si c'est valide → transmet au cuisinier. Ne cuisine rien lui-même.

↓
3
👨‍🍳 Cuisinier (Service) applique la recette

Connaît la recette Margherita : pâte + sauce tomate + fromage. Vérifie les règles : "A-t-on assez d'ingrédients ? Est-ce dans nos horaires ?" Demande au commis d'aller chercher au frigo.

↓
4
🧑‍🍳 Commis (Repository) cherche les ingrédients

Va au frigo : "Donne-moi la pâte" (SELECT * FROM ingredient WHERE type='pate'), "Donne-moi le fromage" (WHERE type='fromage'). Rapporte tout au cuisinier. Ne décide rien seul.

↓
5
👨‍🍳 Cuisinier (Service) prépare et assemble

Mélange les ingrédients, cuit la pizza 8 minutes, vérifie la cuisson. Crée la pizza finale (Entity). Si quelque chose rate en cours de route → annule tout, rien n'est servi à moitié cuit.

↓
6
📞 Standardiste (Controller) emballe dans une boîte (DTO)

Prend la pizza brute (Entity). L'emballe dans un carton propre (DTO). Enlève les informations internes (temps de cuisson, ID cuisine…). Prépare une réponse soignée pour le client.

↓
7
🧑 Client reçoit sa boîte (DTO)

"Voici votre pizza Margherita, bonne dégustation !" — Le client reçoit uniquement ce dont il a besoin : le nom et le prix. Pas les recettes internes, pas les IDs de commande. Code HTTP : 200 OK ou 201 Created.

Flux complet — Côté Spring Boot

Exemple concret : POST /api/rdv — un patient prend un rendez-vous

1
🌐 Frontend consulte l'API

Le patient clique "Prendre RDV" → le navigateur envoie : POST /api/rdv avec le body JSON {"idDentiste": 3, "dateHeure": "2026-05-10T14:00"} + le header Authorization: Bearer <token JWT>

↓
2
🔐 JwtFilter intercepte la requête

Avant même d'arriver au Controller, le filtre lit le header JWT, valide le token, identifie l'utilisateur et injecte son identité dans le contexte Spring. Si token invalide ou absent → 401 Unauthorized automatiquement.

↓
3
🎯 Controller reçoit la requête

@PostMapping déclenche la méthode. @Valid @RequestBody RdvRequest req valide le DTO : date dans le futur ? ID dentiste non null ? Si invalide → 400 Bad Request sans appeler le Service. Si valide → rdvService.prendreRdv(req, user.getUsername()).

↓
4
⚙️ Service — Logique métier

@Transactional : tout ce bloc est atomique. Le Service charge le Patient et le Dentiste, vérifie que le créneau n'est pas déjà pris, vérifie la disponibilité hebdomadaire du dentiste. Si une règle est violée → exception → rollback automatique MySQL.

↓
5
💾 Repository — SQL auto-généré

rdvRepo.existsByDentisteAndDateHeure(dentiste, dateHeure) → Spring génère SELECT COUNT(*) FROM rendez_vous WHERE id_dentiste=? AND date_heure=?. Si créneau libre → rdvRepo.save(rdv) → INSERT INTO rendez_vous (...).

↓
6
🐬 MySQL exécute et confirme

Exécute l'INSERT. La contrainte UNIQUE (id_dentiste, date_heure) garantit aucun doublon même en cas de race condition. Retourne l'ID généré à Hibernate.

↓
7
⚙️ Service — Fin de la transaction

RDV créé avec succès. Le Service envoie un email de confirmation via mailService.envoyerConfirmationRdv(rdv). Puis convertit l'Entity en DTO : RdvResponse.builder().idRdv(rdv.getId()).nomDentiste(...).build(). Retourne le DTO au Controller.

↓
8
🎯 Controller retourne la réponse HTTP

ResponseEntity.status(HttpStatus.CREATED).body(rdvResponse) → le frontend reçoit un JSON propre avec l'ID du RDV, le nom du dentiste, la date — sans aucune donnée sensible interne. Code HTTP : 201 Created.

⚠️ @Transactional — le "tout ou rien" du cuisinier
Si le cuisinier lance la pizza en l'air et qu'elle tombe (exception), il ne sert pas une pizza à moitié cuite. @Transactional garantit la même chose en base : si le save du RDV réussit mais que l'email plante après, MySQL annule l'INSERT automatiquement. Pas de données partielles.
📦

Entity vs DTO — La pizza vs le carton

Pourquoi on ne renvoie jamais l'Entity directement au client

🍕 Entity — RendezVous.java

Ce que Hibernate construit depuis MySQL — usage interne uniquement

idRdv Integer interne
dateHeure LocalDateTime visible
duree Integer visible
statut Enum visible
patient Patient (entity) relation JPA
dentiste Dentiste (entity) relation JPA
factures List<Facture> lazy / infini
soins List<Soin> lazy / infini
❌ Pourquoi pas au client ?
Exposer une Entity directement peut causer une boucle infinie JSON (Patient → RendezVous → Patient…), exposer des données sensibles (mot de passe hashé), et trop coupler le client au schéma interne.
→
Service
convertit

📦 DTO — RdvResponse.java

Ce que le client reçoit — propre, sûr, ciblé

idRdv Integer visible
dateHeure LocalDateTime visible
duree Integer visible
statut String visible
nomDentiste String extrait de l'entity
nomPatient String extrait de l'entity
✅ Avantages du DTO
Pas de données sensibles. Pas de boucle infinie. Le client obtient exactement ce dont il a besoin. Si le schéma change en interne, l'API reste stable.

Les 6 couches en détail

Règles, annotations et responsabilités précises de chaque couche

🎯 Controller @RestController

= Le standardiste du restaurant

  • Reçoit la requête HTTP (GET, POST, PUT, PATCH, DELETE)
  • Valide le body avec @Valid → retourne 400 si invalide
  • Extrait les paramètres avec @PathVariable, @RequestParam
  • Identifie l'utilisateur via @AuthenticationPrincipal
  • Retourne un ResponseEntity<DTO> avec le bon code HTTP
Fichiers : AuthController, RendezVousController, ConsultationController, FacturationController, AdminController, GlobalExceptionHandler

⚙️ Service @Service

= Le cuisinier qui connaît les recettes

  • Porte 100% de la logique métier — vérifications, calculs, règles
  • @Transactional : si une étape échoue → tout est annulé
  • Peut appeler plusieurs Repositories dans la même transaction
  • Lance des exceptions si une règle métier est violée
  • Convertit Entity → DTO avant de retourner au Controller
Fichiers : AuthService, RendezVousService, ConsultationService, FacturationService, AdminService, MailService

💾 Repository @Repository

= Le commis qui va au frigo

  • Interface qui étend JpaRepository<Entity, Id>
  • Spring génère le SQL automatiquement depuis le nom des méthodes
  • Requêtes personnalisées avec @Query("SELECT ...") en JPQL
  • Aucune logique métier — uniquement accès aux données
Fichiers : UtilisateurRepository, PatientRepository, MedecinRepository, RendezVousRepository, SoinRepository, FactureRepository…

🗃️ Entity @Entity

= La pizza brute du cuisinier

  • Chaque classe = une table MySQL
  • Chaque champ = une colonne (@Column(name="...") si snake_case)
  • Relations FK mappées avec @ManyToOne, @OneToMany, @OneToOne
  • FetchType.LAZY partout — évite les requêtes N+1 catastrophiques
  • Ne sort jamais directement dans les réponses API
21 fichiers : Utilisateur, Patient, Medecin, RendezVous, DossierMedical, Soin, Facture…

📦 DTO Request / Response

= Le carton à emporter (boîte propre)

  • Request DTO : ce que le client envoie (body JSON) — annoté @NotNull, @Email, @Size
  • Response DTO : ce que le serveur retourne — sans données sensibles ni relations JPA infinies
// Request : ce que le client ENVOIE
public class RdvRequest {
  @NotNull            private Integer       idDentiste;
  @NotNull @Future     private LocalDateTime dateHeure;
  @Min(15) @Max(120)  private Integer       duree;
}

// Response : ce que le client REÇOIT
@Builder
public class RdvResponse {
  private Integer       idRdv;
  private String        nomDentiste;
  private LocalDateTime dateHeure;
  private String        statut;
  // Pas de mot de passe, pas d'Entity imbriquée
}

🔐 Security JWT

= Le vigile à l'entrée du restaurant

  • JwtUtil : génère et valide les tokens JWT (clé secrète, expiration)
  • JwtFilter : intercepte chaque requête, extrait le Bearer token, valide et injecte l'utilisateur dans le contexte
  • UserDetailsServiceImpl : charge l'utilisateur depuis MySQL par email
  • SecurityConfig : définit quelles URLs sont publiques et quels rôles ont accès à quoi
Flux : Requête HTTP → JwtFilter → SecurityContext → Controller
